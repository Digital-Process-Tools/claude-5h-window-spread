`.github/scripts/check_release_tree.py` builds every `FAIL`/`REVIEW` offender line
with raw `f"{rel}: ..."` interpolation (`off.append(f"{rel}: OS junk ({comp})")` and
similarly throughout `_check_images`, `_check_launchers`, the credential-review
branch), then `main()` prints them one per line (`print(f"FAIL {line}")`). `rel` comes
from a path inside the tree under check -- i.e. from a filename somebody committed.
`name_problems()` already flags a path segment containing a newline as a Windows-bad
character, but the very offender line reporting that catch still embeds the raw,
un-escaped `rel`, so the newline inside it splits the printed line in two: anything
the committer put after the embedded newline renders in the CI log as if it were the
tool's own next line. `hook_command_problems`' offender lines avoid this (`cmd!r`,
Python repr, turns an embedded newline into literal `\n`); the same neutralization is
not applied to `rel` anywhere else in the file.

Found by `oss:auditor` during #12's self-review (Class C: untrusted text forges a
boundary). Ranked `misreports` rather than `forges` because nothing in this repo's own
pipeline re-parses `check_release_tree.py`'s stdout mechanically -- the workflow only
checks the exit code -- so the consumer is a human reading a CI log, not a receipt this
loop parses; whether GitHub Actions' own `::name::` log-command parser would read
something out of an injected line was not verified either way. Non-blocking -- logged
here rather than fixed in #12 because the fix (`rel!r}` or equivalent, consistently,
everywhere a path reaches one of these f-strings) touches a script this diff mostly
carried over unmodified from claude-remember's own reference implementation, which has
the identical pattern; fixing it only here would silently diverge from the upstream
shape without anyone deciding to.
